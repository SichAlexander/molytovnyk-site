This document is a step-by-step engineering tour of the Molytovnyk codebase — from what the app is and how its modules fit together, through the liturgical engine and content pipeline, to the design system, cloud layer, and the development process that ships it.

1. Overview & Purpose

Molytovnyk (Молитовник) is an offline-first Android prayer book for the Ukrainian Greek Catholic Church. It gives parishioners the daily Divine Liturgy with its full ordo, the complete Psalter, a personal and universal prayer library, the liturgical calendar, and an AI-powered spiritual advisor — all in Ukrainian. It is built deliberately for children aged 7+ and for newcomers to the Byzantine / UGCC tradition, with a Kids Mode that simplifies the UI and softens the visual style. Core content ships bundled inside the APK as JSON, so no network connection or account is required to pray.

Current status

Pre-release, in active development toward a first pilot install with the Mukachevo Eparchy. Key facts about where the project stands:

  • V2 redesign is now the default and only UI. The original V1 entry (MainActivity and the legacy :feature:liturgy/:psalter/:prayers modules) was deleted at the Phase 8 cutover (Wave CUT.1); MainActivityV2 is the sole launcher.
  • Pilot hardening is largely complete. Release-candidate hardening, Play Store asset prep, single-parish finalization, and onboarding/nav cleanup have all shipped. Remaining pilot gates are external/owner-paced (production keystore custody, Play Console upload, clergy text sign-off).
  • iOS KMP shell is in progress. :core:domain is multiplatform (JVM + iOS), and a parity-first iOS track (SwiftUI over shared Kotlin, with SKIE Kotlin↔Swift interop) is being built out screen by screen.
The liturgical engine is the most complex part of the app: CalendarService computes Pascha (Butcher algorithm) and resolves tone / feast / movable cycle for any date, and LiturgyAssembler emits a deterministic, ordered list of display blocks from a date + rules + base template. All liturgical content is bundled JSON under app/src/main/res/raw/, loaded into Room at first launch — there is no cloud content backend.

Key features

  • Daily Divine Liturgy — a deterministically assembled ordo combining fixed text with the day's variable chants, scripture readings, and feast-day propers; with an in-place ♪ notation-sheet toggle for the core sung parts.
  • Full Psalter — all 20 kathismas, rendered verse-per-line with per-Slava navigation in a dedicated kathisma reader.
  • Prayer library — personal and universal prayers, plus a prayers hub (rosary / Вервиця, akathist, Canon of the Day).
  • Liturgical calendar — covers the movable cycles (Triodion, Pentecostarion, Octoechos) and fixed feasts, with dual-calendar (Gregorian / Julian) feast resolution.
  • Kids Mode — a child-friendly experience with the Rose / Meadow / Sky palettes and a simplified reading surface.
  • AI Spiritual Advisor (Духовний помічник) — a streaming chat advisor grounded on keyword-retrieved knowledge chunks, behind a default-off flag with an honest offline / no-key fallback.
  • Offline-first — the full Liturgy, Psalter, prayers, and calendar work with no network and no sign-in.

2. Architecture & Module Structure

Molytovnyk is a multi-module Gradle project. The authoritative module list is settings.gradle.kts — when the README's "Project layout" disagrees, settings.gradle.kts wins (the README is slightly stale on the cutover noted below). The codebase splits cleanly into three tiers: a shared :core:* foundation, a set of V2 :feature:* screens that consume it, and the :app entry point that wires everything together. Two pure-JVM :build-logic:* modules provide compile-time tooling and never ship in the APK.

2.2 Dependency boundaries

Dependencies flow strictly downward: feature modules depend on core, and core modules depend on domain — never the reverse. The shared foundation is the load-bearing trio:

  • :core:domain — pure Kotlin (KMP). Knows nothing about Android, Compose, or Room. Highest reuse, zero platform coupling.
  • :core:database — the Room engine + liturgical assembler. Consumes :core:domain; consumed by every :feature:*-v2 module that renders content.
  • :core:designsystem — visual tokens. Consumed by every Compose-bearing feature so colors/type/dimens stay 1:1 with the design spec.

A key asymmetry: :core:data-cloud cannot import :app the way :app imports it. This drives concrete invariants — e.g. notification id allocation. The canonical NotificationIds registry lives in :app, but because :core:data-cloud can't reach up to it, the FCM EventNotificationSpec.atStart() path inlines the same id-range mapping. If one changes, both must change — a documented cross-module mirror, not an accidental duplication.

2.3 Dependency injection

DI is Koin 3.5.6, wired in UstavApplication. Repositories, the AppDatabase, and the LiturgyContentReader are registered as single instances (one per process); ViewModels are injected per-screen. On startup UstavApplication also loads the bundled res/raw JSON content into Room via the readers, so the liturgical engine has its data before the first screen renders.

2.4 Navigation

The app is single-Activity: MainActivityV2 hosts a Compose navigation graph defined in MolytovnykNavGraph (route constants in the MolytovnykRoutes object). There are five bottom-nav tabs:

  • Дім (home)
  • Літургія (liturgy)
  • Молитви (prayers)
  • Спільнота (community)
  • Більше (more)

Psalter, Settings/profile, and parish tools are top-level (non-modal) destinations reached via the More tab — they keep the bottom nav visible (Psalter is also linked from the Prayers list). They are not separate tabs.

Modal routes hide the bottom nav. A route that should get full-screen treatment (prayer session, completion screens, focused forms, the Spiritual Advisor canvas) annotates its MolytovnykRoutes constant with @Modal. The :build-logic:modal-routes-ksp processor discovers every @Modal const val, reads its literal route string, and emits a generated MODAL_ROUTES: Set<String> (package com.njakawaii.molutovnuk.v2.generated). MainActivityV2 imports that set and suppresses the bottom nav for any current route it contains. This replaced the old two-edit footgun (register the composable and hand-maintain a parallel Set) — annotate the constant once and the nav-bar suppression follows automatically; a NavGraphSnapshotTest asserts the generated output matches the graph.

3. The Liturgical Engine

The heart of Molytovnyk is a pure-Kotlin liturgical engine living in :core:domain (a KMP module with JVM + iOS targets, so the same Ordo math runs on Android and on the future iOS shell). Given a civil date it computes the correct Divine Liturgy for that day — the movable cycle, the tone, the commemorated feasts, the variable chants — and assembles a deterministic, ordered list of display blocks ready for rendering. There is no cloud backend: every byte of liturgical content ships bundled in the APK and the engine produces each day's service on demand.

3.1 CalendarService — what day is it, liturgically?

CalendarService (core/domain/src/commonMain/kotlin/.../data/logic/CalendarService.kt) answers the question every other layer depends on: where are we in the liturgical year?

  • Gregorian Pascha (Butcher's algorithm). getOrthodoxPaschaDate(year) computes Easter via the Anonymous Gregorian algorithm. The UGCC new-calendar uses the Gregorian Paschalion, so this is the anchor for the entire movable cycle (e.g. 2026 → 5 April, 2027 → 28 March).
  • Movable-cycle detection. The distance from Pascha classifies the day into one of the movable periods — Triodion (the pre-Paschal weeks, counted backwards), Pentecostarion (Pascha → Pentecost, counted forwards), and the post-Pentecost Octoechos ("по Зісланні") tone cycle. computeMovableSundayCommemoration maps the exact week offset to named Sundays (Publican & Pharisee at −10, Thomas Sunday at +1, and so on).
  • Tone & feast lookup. getLiturgicalDayContext(date, rules, mode, ustavFeastClassHint) resolves the day's tone (glas), afterfeast window, antiphon type, and matching feasts from the annual Ustav rulebook. The hand-tagged Ustav feast_class is authoritative: a hint can only promote the computed rank, never demote it, so great feasts can't be silently downgraded by best-effort engine math.

3.2 LiturgyAssembler — building the Ordo

assembleLiturgy(...) (core/domain/.../data/logic/LiturgyAssembler.kt) takes the day's rules + a base template (the fixed Liturgy skeleton) + a rich-content provider for the variable slots, and walks the template unit-by-unit to emit an ordered List<LiturgyDisplayBlock>:

  • Fixed vs. variable substitution. Each base unit is FIXED or VARIABLE. Variable units (ref_variable) pull their text from the rich-content provider for that day (troparia, kondaki, antiphons, prokimena); feast-specific overrides replace the corresponding slots when a FeastServiceDefinition is present (e.g. the festal entrance hymn or zadostoynyk).
  • Speaker roles. Every emitted block carries a speaker (Диякон / Священник / Хор / Люди) and a coarse engine type — the raw material the rendering mapper (§3.4) classifies.
  • Deterministic & regression-tested. The output is a pure function of its inputs — same date + rules → byte-identical Ordo. This is locked down by "Golden-Ordo" snapshot tests (GoldenOrdoParityTest in :core:domain commonTest) plus LiturgyAssemblerTest and per-feast Ordo fixtures. Because the goldens live in a different module than the JSON they cover, any liturgy-content change must run the cross-module :core:domain:jvmTest sweep — the obvious nearest test passing is not enough.
Completeness, not just exclusion. The template's per-unit targetLiturgy filter is an exclusion mechanism — it can drop units that don't apply to a rite, but it cannot guarantee a rite has any positive content. A LiturgyType with no tagged template (e.g. Presanctified Gifts) would otherwise render the full untagged Chrysostom skeleton. The shared generator short-circuits such types to an honest notice until clergy-verified content lands.

3.3 Dual-calendar resolution (Wave OT.8)

Feast resolution is parameterised by a CalendarMode (com.njakawaii.molutovnuk.domain.logic.CalendarMode): 

enum class CalendarMode { GREGORIAN, JULIAN }

GREGORIAN is the default everywhere — it is the UGCC new-calendar reckoning. JULIAN serves old-calendar parishes. The matcher selects exactly one key field per mode, never OR-ing both: a pre-OT.8 bug OR-ed both fields against one civil date and co-resolved two feasts thirteen days apart on eleven dates of the year.

Inverted-key gotcha — read before "fixing" this. The LiturgicalRule field names are inverted relative to their contents: date_key_julian actually holds the new-calendar civil date and date_key_gregorian holds the old-calendar one. Therefore the matcher does the counter-intuitive thing on purpose:
  • GREGORIAN (new-cal default) matches date_key_julian
  • JULIAN (old-cal) matches date_key_gregorian
This is correct. Do not "obviously" swap the two fields back.

CalendarService.JulianCalendarFlag (mirrored from BuildConfig.ENABLE_JULIAN_TOGGLE) is a warm-path mirror only, read solely by getOrthodoxPaschaDate for the deferred Julian Paschalion offset — it is not read by feast resolution. Fixed-date feast resolution is shipped; the Julian Paschalion offset for movable feasts is still deferred (TODO(F.3): apply Julian Paschalion offset guards the empty branch today).

3.4 The five-role rendering contract

Every assembled block is routed at the rendering boundary into one of five roles by a pure mapper, LiturgyBlockTypeMapper.mapType(block). The roles are the canonical enum LiturgyBlockType — lifted to :core:domain commonMain so the iOS engine routes blocks identically: 

enum class LiturgyBlockType { Rubric, Said, Sung, PeopleSung, Response }
RoleMeaning
Rubric Stage direction / instruction line (e.g. «Диякон», «(тихо)»). Nobody sings it; rendered uppercase, muted.
Said Clergy spoken text — the default narrative body, rendered quieter (opacity 0.72).
Sung Priest / deacon cantillated exclamations & blessings — rare. Matched on a «(співає)» / «(поспівно)» hint in the speaker label.
PeopleSung People-sung long-form: antiphon refrains, tropari, kondak, megalynarion, irmoses, stichera. The default for anything tagged Хор / Choir / Люди / People that isn't a canonical short response.
Response One of the four canonical short cries — Амінь · Господи, помилуй · Подай, Господи · Тебі, Господи — case-insensitive, trailing punctuation tolerated. The most prominent role.
Accent gotcha — the "mapper vocabulary drift" bug. The bundled JSON ships chant text fully accented, with a combining acute (U+0301) on every stressed vowel — «Амі́нь.», «Го́споди, поми́луй.». The CANONICAL_RESPONSE_CRIES set, however, is stored unaccented. Before the fix, the lookup was accent-blind in the wrong direction, so every short cry routed to PeopleSung instead of Response — roughly 65 misclassifications per assembled Liturgy. The mapper's own unit tests passed because their fixtures were also unaccented: the test vocabulary had drifted from production vocabulary. The fix normalises input through a stripAccents (U+0301-removal) step before the set lookup, and the tests now include accented cases lifted verbatim from the bundled JSON so the drift cannot recur.

3.5 Data flow into the engine

All liturgical content is bundled as JSON in app/src/main/res/raw/ — the Divine Liturgy structure (gods_liturgy_fixed.json, antiphons, beginnings), the variable chants (troparia_kontakia.json, prokeimena_alleluia.json, kinonika.json), the annual rulebook (ustav_2025_2026.json), the readings (epistles.json, gospels.json), and the psalter. The pipeline is:

  1. On app start, LiturgyContentReader loads the res/raw JSON into the Room database.
  2. CalendarService resolves the day's liturgical context (Pascha, cycle, tone, feasts, mode).
  3. LiturgyAssembler consumes that context + the base template + the rich-content provider to emit the ordered List<LiturgyDisplayBlock>.
  4. The five-role mapper classifies each block, and the V2 reader renders it.

The whole chain is offline-first and deterministic — there is no network call anywhere in producing a day's Ordo, which is exactly what makes the Golden-Ordo snapshot tests possible.

4. Data & Content Layer

Molytovnyk is offline-first. Every piece of liturgical content — the Divine Liturgy structure, the annual rulebook, all readings, chants, psalter, and the chat knowledge base — ships bundled as JSON inside app/src/main/res/raw. There is no cloud backend for liturgical content; Firebase is used only for the optional Community / parish layer (see §7). On app start, UstavApplication reads these files through LiturgyContentReader (a tolerant Json { ignoreUnknownKeys = true } reader) and hydrates them into Room. From then on, CalendarService + LiturgyAssembler produce each day's Ordo on demand from the local DB — no network required.

4.2 Room database

The local store is AppDatabase, currently at schema version 49 (declared in core/database/src/main/java/.../data/db/AppDatabase.kt). Code generation uses KSP (v2.0.21-1.0.27), not kapt.

Version note: the top-level CLAUDE.md still describes the DB as "v46" in a couple of prose sections — the source of truth is the version = 49 annotation on AppDatabase, confirmed by the per-module core/database/CLAUDE.md. Treat the source annotation as canonical when they disagree.

The database declares ~29 entities. The liturgical/content core includes DailyInfo, Feast, DailyFeast, ServiceText, ServiceTemplatePart, PersonalPrayer, PsalmEntity, KathismaPrayerEntity, and UstavDayRuleEntity, plus the readings/chants tables (ReadingEntity, TroparionKontakionEntity, ProkeimenonAlleluiaEntity, KinonikonEntity) and the Canon-of-the-Day pair (CanonDayEntity / CanonDayItemEntity). Engagement and parish tables — PrayerStreakEntity, StreakStateEntity, IntentionEntity, KathismaCompletionEntity, the Rosary tables, PersonalEventEntity, ParishCacheEntity, NewsItemEntity, and the three Community tables — round out the set.

Migrations live in core/database/src/main/java/.../data/db/v2/Migrations.kt, following the MIGRATION_N_NPLUS1 object pattern. Recent bumps illustrate the two shapes used:

  • Additive — e.g. MIGRATION_48_49 added nullable textUa / versesUa columns to prokeimena_alleluia for the Wave LL liturgy-language track; existing rows untouched, back-filled on the next content re-import.
  • Data-wipe re-hydrate — schema is unchanged but a content table is cleared so the next launch re-imports the bundled JSON (e.g. MIGRATION_36_37 re-hydrating the psalter, MIGRATION_43_44 re-loading the OT chant tables).

Schema bumps are scaffolded with the /add-room-migration skill, and the check-room-migration hook warns when an @Entity changes without a matching migration. During V2 development the DB also falls back to destructiveMigration() — migrations are best-effort until the schema stabilizes.

4.3 RAG / Spiritual-Advisor knowledge base (experimental)

The chat / Q&A corpus is the one piece of content that does not live in Room. KnowledgeBaseRepository loads knowledge_base.json + spiritual_counseling.json from res/raw into an in-memory List<KnowledgeChunkEntity>. RagUseCase then does keyword-only scoring over each chunk's title / tags / text and returns the top-3 (.take(3)) chunks for a query — no vectors, no DB round-trip.

Vector search is deferred. MediaPipe Text Embedder + the cosine-similarity path were removed because libmediapipe_tasks_text_jni.so failed Android 16's 16 KB page-size alignment check and triggered a system warning dialog on every launch (pilot-blocker, issue #463). The embedding field, TextEmbedderHelper, and vectorSearch() are all gone; the keyword path is what ships. Re-introducing semantic search means bumping to a 16 KB-aligned MediaPipe build and reinstating those pieces — a quality lift, not a correctness requirement.

As of Wave RR.5 the chat surface is a real V2 feature (:feature:chat-v2): a streaming Anthropic client in :app (StreamingChatClient, model claude-haiku-4-5) grounds its answer on the keyword-retrieved chunks. It is gated behind the default-OFF spiritualAdvisorEnabled flag, and degrades honestly: with no API key or no network it falls back to a keyword-only OfflineFallback response rather than failing silently.

4.4 User preferences

User-level settings live in UserPreferencesRepository, backed by Jetpack DataStore (not Room). It persists:

  • Dark theme — light/dark toggle.
  • Kids mode — the simplified, child-facing experience.
  • Text scale — accessibility text-size knob (drives LocalTextScale, with damped image scaling).
  • Kids theme color — KidsThemeColor ∈ PINK BLUE GREEN ORANGE PURPLE.
  • Calendar mode — Gregorian (new-calendar, default) vs. Julian, feeding the dual-calendar feast resolution in CalendarService.

5. Feature Modules (V2 Surfaces)

Every user-facing surface ships as its own :feature:*-v2 Gradle module, each consuming the shared :core:designsystem tokens and the :core:domain / :core:database liturgical engine. All wiring lands in MainActivityV2 via the Compose MolytovnykNavGraph. Below is one subsection per module, naming the real screens and ViewModels in the current source tree.

Home — :feature:home-v2

The landing tab. Renders a time-of-day greeting, the daily card (feast / readings), the prayer-task list with streak credit, an upcoming-events strip, and the permission / nudge banners stacked above the feast stripe. It also owns the More tab, onboarding, settings, and reminders, so it is by far the largest feature module.

Liturgy — :feature:liturgy-v2

The Divine Liturgy reader. It renders the assembled List<LiturgyDisplayBlock> through the five-role rendering contract and offers an in-place ♪ notation-sheet toggle (Wave C.5): for the core-5 sung parts the body swaps to a ScoreView backed by ChantRepository. The Liturgy table-of-contents is an in-screen sub-state (isTocShown) rather than a separate route — drawn as a full-screen overlay in the single-pane reader, or as a persistent inline pane in the expanded multi-pane (tablet) layout.

  • ViewModel / support: LiturgyViewModelV2, LiturgyAssemblyOrchestrator, LiturgyBlockTypeMapper (the five-role mapper at the V2 boundary), LiturgyFeatureFlags.

Calendar — :feature:calendar-v2

The liturgical calendar. A month grid drives a per-day detail sheet and a full-text search; the assembler layer resolves the movable + fixed cycles, the vestment color, and the fast intensity for each civil date.

6. Design System & Visual Layer

The visual layer of Molytovnyk lives in a single dedicated Gradle module, :core:designsystem. It holds the V2 design tokens (palette, typography, spacing, shapes, animations), the theme machinery, and a library of shared Compose components. Every :feature:*-v2 screen draws exclusively from this module — features never hardcode a hex color, an sp size, or a dp dimension.

Single source of truth. The canonical token source is design-system/project/colors_and_type.css. Every val in the theme files is a direct port of a CSS custom property — the Kotlin files carry the original --token-name in a trailing comment so the mapping stays auditable. The older design/ folder is historical only; do not source tokens from it.

6.1 Token architecture

The theme package (core/designsystem/.../theme/) decomposes the CSS into five token files plus the theme plumbing:

FileOwns
Color.ktRaw pigment Color(0xFF…) values, ported 1:1 from the CSS. Three palette families: Candlelit Nave (dark — the primary prayer mode), Vellum (light — daytime reading), and the Kids pigments.
Type.ktFont families + the Material 3 Typography table + ~45 standalone custom roles.
Dimens.ktMolytovnykDimens — spacing (SpaceXs…Space2xl), ScreenPad, and the card radii (RadiusCard 20dp, RadiusCardSm 18dp, RadiusCardXs 16dp).

Animations.ktMolytovnykAnimations — easing curves and durations.

6.2 Typography — the Cormorant & Inter idiom

Three font roles carry the whole system: Cormorant Garamond (display / headings), Noto Serif (liturgical body and prayer text), and Inter (UI chrome). The Material 3 roles are produced by a builder:

fun molytovnykTypography(scale: Float = 1.0f): Typography

The 11 M3 roles map onto the CSS scale (e.g. displayLarge ← --text-hero ≈ 96sp Cormorant; bodyLarge ← --text-body-lg 18sp Noto Serif). Anything the M3 vocabulary can't express lives as a standalone named TextStyle — Eyebrow, Streak, NavLabel, the five LiturgyBlock* roles, and the cluster of banner/dialog/score roles promoted out of inline tuples across the Polish sprints. Role names follow the designer's baseline lexicon (Cormorant-and-Inter idiom, no Material vocabulary, no abstract scale numbers).

Fonts currently fall back to system serif/sans. CormorantGaramond and NotoSerifBody alias FontFamily.Serif; InterUi aliases FontFamily.SansSerif. Embedded variable TTFs (the [wght] axis) were tried but layoutlib (Paparazzi) cannot resolve FontVariation.Settings(…) and threw on every snapshot — the re-introduction path is N static-weight TTFs per family. Visual fidelity arrives with that swap; the scale metrics are already correct.

Text-scale accessibility & damped image scaling

User text size is a first-class accessibility control. LocalTextScale (range 0.8f..1.6f, 7 slider stops, persisted in UserPreferences.textSizeScale) is folded together with a device-size-class bump (LocalDeviceTextScale — 1.0× on small sw360 screens, 1.07× on the dominant sw411+ bucket) into a single LocalEffectiveTextScale. M3 roles are pre-scaled by molytovnykTypography(scale) at theme-compose time; standalone roles call .scaledByLocalTextScale() at their use site.

Images do not track text 1:1 — they would crowd small screens. A damping curve keeps text scaling fully while images grow gently:

imageScale = 1 + (textScale - 1) * IMAGE_SCALE_DAMPING   // IMAGE_SCALE_DAMPING = 0.5f
// textScale 1.30 → imageScale 1.15   (image grows 15%, not 30%)
// textScale 1.60 → imageScale 1.30
// textScale 0.80 → imageScale 0.90

Exposed as Dp.scaledByLocalTextScale() / the pure helper dampedImageScale(textScale). The rule is tokens 1:1, no scaling on padding — layout spacing, hairline borders, and ≤24dp chrome icons stay fixed in dp. A 280dp candle hero on a 360dp screen overflows at 1.30× text but fits comfortably at the damped 1.15×.

6.3 Kids Mode palettes

Kids Mode swaps the entire palette for one of three iconographically-coded variants, chosen by the child at onboarding and persisted in prefs. The KidsPalette enum carries both a light and a dark variant per palette:

  • ROSE (Троянда) — Theotokos warmth, the dusty rose of the мафорій Богородиці.
  • MEADOW (Лука) — monastic Carpathian green.
  • SKY (Небо) — angelic lapis, the bleached azure of icon backgrounds.

Each palette overrides accent/surface roles while keeping the structural token contract. The dark variants follow a documented role-flip rule (dark primary becomes the lifted accent for CTAs and titles; deep drops to borders; darkText takes body-text duty). This V2 enum is distinct from the legacy V1 KidsThemeColor (PINK / BLUE / GREEN / ORANGE / PURPLE).

6.4 Shared components

The components package holds ~50 composables. Three are load-bearing:

  • MolytovnykCard + MolytovnykButton — the shared card/button primitives from the Material-native polish initiative. MolytovnykCard(tier = Primary/Nav/Compact, …) gives the three radius tiers (20/18/16dp), solid-or-brush fill, candle-flame glow + celebratory leadingStripe, ripple + Role.Button semantics, and opt-in light-theme elevation. MolytovnykButton(style = Primary/Secondary/Link) wraps the three M3 button kinds in the byzantine palette. New home/feature surfaces compose these instead of hand-rolling clip → background → border → clickable → padding.
  • LiturgyBlockText — the renderer for the five canonical liturgy text roles. It maps a LiturgyBlockType (Rubric · Said · Sung · PeopleSung · Response, the enum now lifted to :core:domain commonMain so iOS shares it) onto the matching LiturgyBlock* typography role plus a per-state color from the active theme. The five-role contract is the designer round-trip recorded in design-system/response/2026-05-19-liturgy-roles/REVIEW.md.

6.5 Dark-theme parity & token-leak enforcement

Dark/light parity is structural: pigments are never referenced directly inside features — they go through semantic role tokens that resolve per variant, so a screen written once renders correctly in both themes (and in all three Kids palettes). The discipline is enforced by custom Detekt rules in :build-logic:detekt-rules (a pure-JVM module registered under the molytovnyk-token-leak rule-set, consumed by the root detekt block):

  • HexColorLiteralRule — flags any hardcoded Color(0xFF…) in feature code.
  • BareSpDpLiteralRule — flags raw sp/dp literals that should be a MolytovnykDimens constant.
  • InlineTextStyleRule — flags inline TextStyle(…) that should be a named typography role.

The token-source module :core:designsystem itself is allowlisted at the root Detekt level — it is the one place raw literals legitimately live.

6.6 Visual regression — Paparazzi as a Definition-of-Done gate

Screenshot tests are a hard merge gate, not a nicety. Any PR touching a :feature:*-v2 *Screen.kt / *Route.kt MUST land with at least one Paparazzi @Test covering the modified surface (one @Test per visual state: default · loading · error · empty · disabled), with the recorded PNG under <module>/src/test/snapshots/images/. Paparazzi is the daily driver — pure-JVM via Robolectric layoutlib, working on Windows and CI. The docs/screenshot-tests.md runbook is canonical; the /verify-screen <screen-file> skill scaffolds the test and records baselines.

Two recurring gotchas.
  • One @Rule Paparazzi per test class. layoutlib is single-instance per test class — two @get:Rule Paparazzi fields throw IllegalStateException at runtime (not compile time). Split device variants into separate classes (e.g. HomePaparazziTest + HomePaparazziSmallScreenTest).
  • Token / typography churn drifts baselines everywhere. Any edit to a theme/ file (Type.kt, Color.kt, Dimens.kt, Shapes.kt, Animations.kt) shifts sub-pixel font rasterization across every Paparazzi-bearing module — not just the one you touched. Re-record the full set via /regression-sweep (which encodes the fan-out rules) and ship the regenerated PNGs in the same PR. A token PR without a baseline diff is rejected, because color/typography shifts are invisible at code-review time.

7. Firebase, Cloud & Backend Functions

Molytovnyk is offline-first. The entire liturgical engine — the daily Divine Liturgy, psalter, calendar, and personal prayers — is served from JSON bundled in res/raw and a local Room database; none of the core content is cloud-backed. Firebase exists only to power the social and parish layer: Community/parish events, prayer circles, presence, capability-gated clergy tooling, and push notifications. The app builds, runs, and stays fully useful with no google-services.json at all.

Dormant-guard invariant. Every gateway in :core:data-cloud checks FirebaseApp.getApps(context).isEmpty() and returns null / no-ops when Firebase is absent. CI stubs google-services.json with dummy ids and every cloud feature no-ops cleanly. New gateways must follow the pattern — DormantGuardTest guards it. Real project: molytovnyk-40207 (Blaze plan, which unlocks presence, cloud psalter, and FCM push).

7.1 :core:data-cloud — the Firebase boundary

This module is the app's single seam onto Firebase. Nothing else imports the Firebase SDK directly. It owns four responsibilities:

  • Auth gateways — FirebaseAuthGateway (anonymous-first, upgradeable to Google via linkWithCredential), OnboardingAuthGateway, GoogleSignInLauncher. Auth state is exposed as a StateFlow<AuthState>.
  • App Check — AppCheckGateway attests requests so only the genuine app can reach Firestore / Functions.
  • Firestore cloud sources — one typed source per surface: FirestoreEventCloudSource, FirestoreCircleCloudSource, FirestoreOccurrenceCloudSource, FirestoreSubscriptionCloudSource, FirestorePsalterIntentCloudSource / …RotationCloudSource, FirestoreLiturgyScheduleCloudSource, FirestoreParishCloudJoiner, news/completion/feature-flag sources, plus FirebaseRemoteConfigSource (force-update gates) and RtdbPresenceSource (Realtime Database presence).
  • FCM topics + notification specs — FcmTopicGateway, MolytovnykMessagingService (inbound routing), and the per-domain notification channels + specs (EventNotificationSpec, CircleNotificationSpec, QuietHoursPrefs).

Capability gating. Custom claims are stamped per-parish onto the Firebase Auth token; hasCap(capability) in firestore.rules reads request.auth.token.capabilities[parishId][]. The catalogue (in functions/src/capabilities.ts) includes event.edit_recurrence, event.cancel_occurrence, event.send_announcement, event.view_minor_data, psalter.edit_intent, eparchy.promote_event, and clergy_reviewer.

7.2 Firestore security rules & the test harness

firestore.rules is an invariant layer, not a convenience — it is the server-side authority that no client can bypass. It enforces membership gates, the per-parish capability claims above, and a schemaVersion: Int on every document (a future migration hook present from day one). Realtime Database has its own database.rules.json for presence, and query indexes live in firestore.indexes.json (the at-start dispatcher needs a scheduledWallClock COLLECTION_GROUP index declared there — prod-breaking if missing).

Rules are exercised by a dedicated harness in firebase-rules-tests/ (molytovnyk-firebase-rules-tests), which runs synthetic payloads against the deployed rules under the Firebase Emulator via @firebase/rules-unit-testing: 

cd firebase-rules-tests && npm test
# firebase emulators:exec --only firestore … "jest --runInBand"

7.3 Cloud Functions (functions/)

Firebase Cloud Functions v2, Node.js 22 / TypeScript, region europe-west3. Dependencies are firebase-admin + firebase-functions; deploy with npm --prefix functions run build && firebase deploy --only functions. The client is the sole producer of event/occurrence docs — no function creates them; the TS layer only reads, queries, and fans out. Main triggers:

FunctionTypePurpose
setRoleCapabilitiesCallableStamp capability claims on the Auth token (audit-before-action).
onOccurrenceUpdatedFirestore triggerFan out intent_updated FCM to the event topic.
onOccurrenceStatusChanged / onEparchyOccurrenceStatusChangedFirestore triggerEmit reminder_at_start FCM when an occurrence flips to live (both D-009 stores).
onParishSubscriptionWritten / onEparchySubscriptionWrittenFirestore triggerMaintain denormalized subscriptionCount.
onPsalterIntentUpdatedFirestore triggerFan out psalter_intent_updated FCM to the psalter topic.
aggregatePresenceRTDB triggerMaintain /presenceCount from /presence children.
dailyRolloverScheduler (daily, Kyiv)Flip open occurrences to completed / missed. Idempotent.
atStartPushScheduler (every min)Flip due occurrences to live via one collectionGroup range query; the status-change triggers then send the push.

Two backend invariants are absolute: audit-before-effect (every callable writes an audit entry before any side effect; if the audit fails the function aborts and no side effect occurs) and the D-009 dual-store (parish-nested parishes/{parishId}/events/… and eparchy-flat eparchyEvents/… paths carry matching trigger logic). The occurrence start-time contract also splits two names that look unifiable but must not be: the doc field is scheduledWallClock (Kyiv wall-clock ISO), while the FCM wire key is scheduledAt.

7.4 FCM & the notification-id registry

Inbound pushes route by topic. Producers in functions/src (topicForEvent / topicForCircle / topicForPsalter) build events_{eventId}, circles_{circleId}, and psalter_{parishId}; MolytovnykMessagingService dispatches by the matching prefix to typed handlers, and the data payload's type field (intent_updated, psalter_intent_updated, reminder_at_start) selects the handler.

On the device side, NotificationIds is the single source of truth for every NotificationManager.notify(id, …) integer — a duplicate id silently dismisses the earlier notification, so three subsystems are split into disjoint reserved ranges:

RangeCategoryProducer
1000..1099Local remindersfixed REMINDER_MORNING = 1001, REMINDER_EVENING = 1002, ANGEL_DAY = 1003
2000..2999Events (FCM)eventNotificationId(eventId) — start + abs(hash) % width
3000..3999Circles (FCM)circleNotificationId(circleId, slot)
Two real-world gotchas.
  • FCM topic names forbid /. Topic names must match [a-zA-Z0-9-_.~%]+. An early events/{id} form was rejected by both the admin send() (error silently swallowed by the emitter) and every client subscribeToTopic() — so no events / circles / psalter push delivered in production until the separator was renamed to _ (#1221). The producer builders and every consumer prefix must use the identical format; a one-character drift fails silently.
  • The id formula is duplicated by design. :core:data-cloud cannot import :app, so CircleNotificationSpec.from / EventNotificationSpec inline the same range + hash math that lives in NotificationIds. If the range or formula changes in one place, change both.

8.2 Test stack & conventions

The suite is roughly 55 *Test.kt unit-test files under app/src/test (plus a debug-scoped tag test under testDebug, instrumented tests under androidTest, and per-module tests in the :feature:*-v2 modules). Key suites guard the liturgical engine — CalendarService (Pascha + movable cycles), LiturgyAssembler (rule-based substitution), pericope-reference parsing, and feast Golden-Ordo snapshots.

  • Stack: JUnit4 + kotlin-test + kotlinx-coroutines-test. Instrumented tests add Turbine + Compose UI test rules. Use runTest {} for coroutine tests.
  • Fakes, not mocks. This is a hard convention — zero MockK/Mockito imports exist project-wide. All test doubles are Fake<InterfaceName> classes that implement the real interface, backed by a MutableStateFlow and mirroring real semantics (REPLACE-on-conflict for DAOs, sorted queries where applicable). For controllable error paths, fakes expose var isNextOpSuccessful / var errorToThrow / fun reset(). Do not introduce MockK or Mockito for new tests.
  • Canonical fakes live in the :core:database testing package (e.g. FakeUserPreferencesSource for DataStore, FakeCommunityDao for DAOs); reference them before inlining a new private class fake.
  • Scaffolding: the /unit-test and /test-scaffold skills generate correctly-imported test files following these conventions.

8.3 Visual regression — Paparazzi as a DoD gate

Any PR that touches a :feature:*-v2 screen must land with a Paparazzi @Test. Paparazzi renders Compose previews to PNG via a pure-JVM Robolectric layoutlib path (no emulator) and fails the build when a committed baseline doesn't match the freshly-rendered output. 8.4 Pre-release functional QA — CORE vs FULL

On top of the automated layers, repeatable on-device functional testing runs in two tiers (hub: docs/qa/README.md), driven via /qa-run core|full:

8.5 CI model — local gate, remote certification

The merge gate is local Gradle (the regression-watcher / /regression-sweep sweep). Remote GitHub Actions CI is a certification layer, not a blocking gate — branch protection is unavailable on this private repo's plan, so the remote check blocks nothing structurally.

The .github/workflows/ci.yml pipeline runs three jobs:

  • Build (debug) + JVM tests — one Gradle pass over :app:assembleDebug :app:lintDebug test :core:domain:jvmTest, then a Paparazzi verifyPaparazziDebug sweep across the seven baseline-owning modules. CI stubs app/google-services.json (the real file is gitignored) so the build succeeds without Firebase secrets.
  • Events Firestore rules unit tests — JDK 21 + Node 20, runs the rules suite against the Firestore emulator (firebase emulators:exec).
  • iOS KMP framework + tests (macOS) — currently quarantined (if: false) pending a stable macOS runner; not a required check, so it doesn't block merges.
  • Red CI on main is a 24-hour fix-or-remove item. A red certification certifies nothing — fix within 24h, or quarantine the failing job/test with a tracked issue. /sprint-close pre-flight blocks a sprint close while the latest main run is red and older than 24h.
  • Self-hosted runner. Because the repo is private, GitHub-hosted minutes are billed and an account-billing lapse instant-fails every hosted run. CI is pinned to a self-hosted GitHub Actions runner that consumes no billed minutes; setup is in docs/ci-self-hosted-runner.md.
  • No-infrastructure fallback. scripts/dev/local-ci.sh reproduces the entire CI build job locally (stub google-services.json → assembleDebug + lintDebug + test → 7-module Paparazzi verify), so certification can happen with no runner and no billing.

8.6 Development process — trunk-based, wave-driven

Trunk-based branching. main is the only long-lived branch and must always be green. Work lands via short-lived (≤2-day) feature branches named claude/<scope>/<slug> (lowercase-hyphenated; scopes include wave-a…wave-g, fix, chore, exp). The default merge style is a merge commit (gh pr merge --merge --delete-branch); see docs/branching.md.

Push to the sichalexander remote, not origin (njakawaii73 is read-only). Before planning or delegating any work, git fetch sichalexander and treat sichalexander/main — not local main — as authoritative; the local clone goes stale fast under parallel sessions.

Wave / sprint model. Work is tracked in three layers: markdown for the spine (docs/ROADMAP.md, docs/SPRINT.md, docs/BACKLOG.md), GitHub Issues + Milestones for the per-task layer, and slash commands for upkeep. One sprint = one Wave step (e.g. A.2, RR.5, LL). The lifecycle commands are /sprint-plan (open a sprint + file wave-task issues), /sprint-status (read-only dashboard), and /sprint-close (archive + retro). Before picking up an issue, always run gh issue view <N> to check state/assignee/comments — parallel sessions occasionally land on the same issue.

Agent/skill SDLC toolkit. A sizable in-repo toolkit drives the development loop: a large library of skills (.claude/skills), a set of specialized agents (.claude/agents, e.g. code-reviewer, design-reviewer, regression-watcher, qa-lead), and slash commands (.claude/commands). The full inventory is maintained in AGENTS.md.
